# Per-world hand-maintained config

`asset-world-<id>/` is **generated** — `render-assets.sh` overwrites it, so editing
files in there loses your changes on the next re-render. Keep per-world settings
here instead. This directory is tracked in git; `asset-world-*/` is not.

    world-conf/<world-id>/<filename>

`<world-id>` is the `WORLD` value from `.env.world-<id>`, e.g. `world-conf/midrate/`.

Two behaviours, picked by filename:

| filename | behaviour |
| --- | --- |
| `battle_conf.txt`, `map_conf.txt`, `char_conf.txt`, `inter_conf.txt` | **appended** to the rendered file |
| anything else | **copied** into `asset-world-<id>/` |

Appending works because rAthena assigns settings as it reads, line by line, so the
last occurrence of a key wins (`battle_config_read`, `map_config_read`). Your
values land after the template's and override them — without losing the
env-driven ones the template supplies.

The copy case is how you supply the `conf/import` files this script does not
render — `groups.yml`, `atcommands.yml`, `log_conf.txt`, `script_conf.txt`,
`packet_conf.txt`, `inter_server.yml`. The world mount replaces *all* of
`conf/import`, so the image's copies are invisible inside a world container and
anything custom must arrive this way.

Example — `world-conf/midrate/battle_conf.txt`:

    base_exp_rate: 1500
    job_exp_rate: 1500
    item_rate_common: 800

Then `./render-assets.sh --env-file .env.world-midrate` and restart the world.

Note: `render-assets.sh` refuses to silently destroy a hand-edited file. Every
rendered file carries a `GENERATED by render-assets.sh` marker; if the output
lacks it, the script saves a `.handedited-<timestamp>` copy and warns before
overwriting.
